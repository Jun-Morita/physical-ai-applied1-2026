# レポート用の試行錯誤の記録

最終課題のレポート（`説明資料_PAI最終課題_<アカウント名>.pdf`）に織り込むため、開発中の試行錯誤を「問題 → 原因 → 対策 → 結果」で整理する。課題要件では、反省点や考察の記載も評価の対象になる（[課題要件](final-project-requirements.md)）。詳しい経緯と日付は [計画書](project-plan.md) にある。数値はすべて実測で、オフラインのJSBSimの結果はFlightGearの結果と区別して書く。

## 1. タスクの設計

| 判断 | 理由 |
| --- | --- |
| 操作はエルロン・エレベーター・ラダー・スロットルの4つ。フラップ・トリム・ブレーキは固定 | 自由度を絞り、少ないデータで学べる範囲にする。C172Pは空中開始の5秒後に機体側のスクリプトがフラップとスロットルを上書きするため、検知して戻す |
| 接地後5秒で終了し、減速は対象外 | 動画を1〜3分にまとめるため |
| 開始位置を乱数でずらす（評価用は番号1000以上） | 同じ飛行の丸覚えを防ぎ、学習に使っていない開始位置で評価するため |
| 接地の判定を項目別に厳しく（脚の損傷は失敗） | 「着いたかどうか」ではなく、接地の質を比べるため |

## 2. 試行錯誤

### 2.1 人の操縦では成功データが集まらない
- **問題**：ゲームパッドでの手動着陸は、17回中2回しか全項目に合格しなかった（バウンド、中心線のずれ）。
- **対策**：PID制御の自動着陸スクリプトを作り、お手本として使う。人の飛行と同じ審査（全項目の合格・動画確認・ラベル付け）を通したものだけを学習に使う。
- **結果**：自動着陸はFlightGearで安定して合格するようになった。

### 2.2 滑走路の位置が355 mずれていた
- **問題**：自動着陸の動画を見たユーザーが「滑走路の端ぎりぎりを狙いすぎ」と指摘した。
- **原因**：シナリオの進入端は、現実の最新データ（`RJTT.threshold.xml`）を使っていた。風景に描画される滑走路（`apt.dat`）より355 m手前にあった。地表の標高から「一致している」と判断していたのは誤りだった。
- **対策**：描画と同じ `apt.dat` の座標に直した。接地の目標を、ICAOのエイミングポイント（進入端から400 m）に向かう3度経路にした。
- **結果**：自動着陸は進入端から約467 m（目標点の約67 m先）に接地するようになった。

### 2.3 判定が厳しすぎて、柔らかい接地を不合格にしていた
- **問題**：自動着陸24回のうち10回が「降下率」だけで不合格だった。
- **原因**：引き起こし後に車輪が地面から約3 cmの高さで浮き、そっと接地していた。接地直前の降下率が−0.05 ft/s（わずかな上昇）で、下限の0を割っていた。
- **対策**：下限を−0.5 ft/sにした（ユーザー判断）。バウンドは別の項目で判定する。
- **結果**：24回すべてが合格した。同様に、バウンドの判定も「接地後に2 ft以上浮いたら」に見直した（手動飛行で0.5 ft以下の小さな跳ねを不合格にしていたため）。

### 2.4 収録の不具合
- **画像と操作の対応**：自動着陸は、画像を撮るたびにシミュレーションを止める。そのため、「一時停止をまたぐ組は除く」という規則で、画像がすべて学習から除外されていた。止めた瞬間の画像・状態と、その状態に対するお手本の操作を1組にする方式に変えた。
- **フラップ上書きの記録漏れ**：一時停止を待つ間に受け取った状態では、上書きを確認していなかった。15回の飛行に1行ずつ、上書き中の行（フラップ1.0、スロットル0.75）が混ざっていた。収録側を直し、収録済みの飛行は記録が残る行だけを学習時に除いた。

### 2.5 MLPは学習データ上は正確でも、飛ばすと着陸できない
- **問題**：自動着陸25回で学習したMLPは、検証誤差が0.00011と小さかった。それでもオフラインで5回中1回、FlightGearでは番号1000で不合格だった（経路より75〜120 ft低くなり、滑走路の479 m手前に接地）。
- **原因**：お手本は常に経路から2 ft以内を飛ぶため、「経路から大きくずれた状態」の手本がない。少しずれると戻し方を知らず、ずれが広がる（模倣学習の分布シフト）。
- **検討**：操作へのノイズ注入（DART）、DAgger、開始距離を1/2・1/4にする案（ユーザー提案）を比べた。ノイズは使わない方針になった（ユーザー判断）。
- **対策**：開始時のずれを広げた自動着陸を23回追加した（高さ±150 ft・横±150 m、距離1・1/2・1/4）。評価は標準の開始条件だけで行う。

### 2.6 オフラインのシミュレーターの不具合で、比較の結論を誤った
- **問題**：オフライン（JSBSimを直接動かす）での比較で、接地後に機首が回って滑走路を外れる失敗が多発した。
- **原因**：FlightGearはラダーの値の符号を反転してJSBSimに渡し、前脚の沈み込みからC172Pの前輪の操向を有効にする。オフラインではどちらも再現しておらず、左ラダーで機首が右に回り、前輪も曲がらなかった。FlightGearの実データ（左ラダーで2.8°のずれが0.7秒で戻る）と比べて気づいた。
- **結果**：修正後、25回のMLPはオフラインで8/10に改善した。修正前の比較の結論はすべて無効にした。
- **教訓**：検証用のシミュレーターは、本番と同じ操作で同じ挙動になるかを先に確かめる。

### 2.7 自動着陸の失速と着水
- **問題**：開始時のずれを広げた27回のうち3回が、進入中に42 ktまで減速して失速し、海に落ちた。
- **原因**：スロットル全開でも速度を保てておらず、エンジンの出力不足が疑われる（ずれの大きさとは無関係）。
- **対策**：自動着陸に無理な回復制御は加えず、墜落・着水したら収録を自動終了し、不合格として残す（ユーザー判断）。原因を確かめるため、終了時のエンジンの状態を記録する。

### 2.8 MLPは学習ごとのばらつきが大きい
- 48回で学習したMLPは、オフラインで0/10だった。学習の乱数を変えると0〜3/10、直前の操作量を入力に加えても0/10。検証誤差（0.00009〜0.002）と着陸の成否は一致しなかった。
- 単純なMLPの改良に時間をかけず、課題の本題であるSmolVLAの追加学習前後の比較に進んだ。

### 2.9 SmolVLAの追加学習前後（FlightGear、番号1000）

| モデル | 結果 |
| --- | --- |
| 学習前 | 開始直後から極端な操作で左に100°傾き、13秒で海に落ちた |
| 追加学習3000ステップ | 234秒間、傾き±7°以内で安定。降下せず約800 ftを保ち、滑走路を越えて進入端から3310 m・右に102 mに接地 |
| 追加学習15000ステップ | 前半は約850 ftまで上昇し、進入端を過ぎてから降下。進入端から2732 m・右に103 m（滑走路の横）に、降下率0.5 ft/s・機首上げ3.5°のなめらかな接地 |

- **原因の調査**：機体の状態は固定の値で割って入力していた（高さ÷1000 mなど）。経路から150 ftずれても入力値は0.046しか変わらず、高さのずれがほとんど見えていなかった。
- **対策**：学習データの平均と標準偏差で正規化し、その値をモデルと一緒に保存して推論でも使う。
- **結果**：正規化して6000ステップ学習したモデル（`runs/vla/c172p-expert-wide-norm-6000`）は、初めて経路に沿って降下した。前半40秒は経路から±15 ft以内、その後は経路より50〜70 ft低いまま安定し、中心線からのずれは進入中±10 m以内だった。滑走路上（進入端から181 m）に、降下率0 ft/s・機首上げ4.1°・52 ktで接地し、脚の損傷もなかった。ただし、引き起こしの間に左へ流れ（接地時に中心線から−26.7 m、機首方位−5.6°）、接地後に滑走路の左端（−41 m）を越えたため、中心線・機首方位・滑走路内の滑走の3項目で不合格だった。

### 2.10 学習前後の比較（FlightGear、評価用の番号1000〜1004）
比較は `runs/compare/vla-norm-6000-vs-base.json`。全項目に合格した飛行は、前後とも0回だった。そこで、項目ごとの合格数も集計した（比較ツールに追加）。

| 項目 | 学習前（5回） | 学習後（正規化＋6000ステップ、5回） |
| --- | --- | --- |
| 接地まで飛べた | 0 | 5 |
| 墜落なし・脚の損傷なし | 0 | 5 |
| 降下率・バンク・主脚からの接地 | 0 | 5 |
| 機首方位 | 0 | 3 |
| バウンドなし | 0 | 2 |
| 接地位置（0〜900 m） | 0 | 1 |
| 中心線（15 m以内） | 0 | 1 |
| 滑走路内の滑走 | 0 | 0 |

- 学習前は、5回とも開始15〜19秒で機体が裏返り（傾き約180°）、海に落ちた。
- 学習後は、5回とも滑走路付近まで進入し、柔らかく接地した（降下率0〜2.7 ft/s）。ただし、進入中に経路より50〜80 ft低めを飛び、4回は進入端の53〜535 m手前に接地した。接地時には中心線から左右に14〜41 mずれた。

### 2.11 学習量を増やして、初めて全項目に合格（FlightGear、番号1000〜1004）
比較は `runs/compare/vla-norm-15000-vs-base.json`。正規化したまま15000ステップ（学習用画像を約12周）学習したモデル（`runs/vla/c172p-expert-wide-norm-15000`）は、5回とも接地帯（進入端から195〜574 m）に接地した。番号1000は接地目標の400 m点のほぼ真上（396 m）に接地し、全11項目に合格した。ユーザーが動画で着陸を確認した（2026-10-13）。

| 項目 | 学習前 | 正規化＋6000ステップ | 正規化＋15000ステップ |
| --- | --- | --- | --- |
| 接地位置（0〜900 m） | 0 | 1 | 5 |
| 中心線（15 m以内） | 0 | 1 | 4 |
| 滑走路内の滑走 | 0 | 0 | 4 |
| 機首方位 | 0 | 3 | 3 |
| バウンドなし | 0 | 2 | 2 |
| 全項目に合格 | 0 | 0 | 1 |

- 6000ステップで見られた「経路より低め」の癖は消え、進入中の高さのずれは最大15〜74 ftになった。
- 不合格の4回は、バウンド（2.2〜3.6 ft、基準2 ft）と、接地時の機首方位のずれ（5.3〜12度、基準5度）が主な原因だった。
- 検証の損失は6000ステップで0.0104、15000ステップで0.0086と小さな差だったが、飛行の結果は大きく変わった。損失の値だけでは学習量の判断ができない。

## 3. 考察の候補
- お手本を真似る学習では、お手本が「失敗から戻る」場面を見せないと、少しのずれから崩れる。データの量より、状態の幅が重要だった。
- 検証誤差の小ささは、実際に飛ばしたときの成否を保証しない。評価は必ずシミュレーターでの飛行で行った。
- 画像と言語の事前学習モデル（SmolVLA）でも、数値の入力の前処理（正規化）が性能を大きく左右した。
- 開発用の高速なシミュレーターは便利だが、本番との違い（符号や機体側の処理）が結論を誤らせる。
