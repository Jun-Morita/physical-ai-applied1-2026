# 最終課題：人の操縦から学ぶAIの着陸

## 合意した方向性

- タスク：滑走路が視界に入っている最終進入から着陸する。
- 空港：羽田空港（HND / RJTT）。初期プリセットは34Rへの進入。
- 機体：実在機を模擬したモデルを使用する。2026-09-27に、旅客機はBoeing 747-400（GE CF6-80C2B1F）、戦闘機はF-14Bに確定した。2026-09-28にCessna 172P（FlightGear基本データ同梱版）を追加し、3機種で着陸課題に取り組む。3機種の操縦・性能は未検証。詳細は [機体選定](aircraft-selection.md) を参照。
- データ収集：受講者がゲームパッドで操縦し、機体状態と操縦入力を記録する。
- AI：操縦データからの模倣学習を軸にする。2026-10-03にSmolVLAの追加学習と学習前後の比較を採用。数値入力MLPも比較対象として保持。
- 利用可能な環境：WSL2上のUbuntu 22.04.5、RTX 3060（12GB）、WindowsにUSB接続したLogicool F310。CPU・RAMは未確認。
- Python環境管理：uv。

## 当初の構成案（下記の実装方針で更新）

Windows側でFlightGearを動かしてゲームパッド入力を受け、WSL側でPythonによる学習・記録を行う構成で環境構築を進める。飛行物理にはJSBSimを使用する。FlightGear内で物理・機体システムを動かす構成を優先し、Pythonとの通信経路は今後検証する。
AIの入力は、まず数値状態から始める案。カメラ画像を入力するかは未決定。
最初は昼間・無風・他機なしとし、機体の重量・燃料・フラップ設定を固定する案。
最終進入からフレア、接地、減速までを対象にし、タキシングは初期範囲に含めない案。
これはシミュレーション課題の設定であり、現実の羽田の運航手順を再現するものではない。

## 羽田のデータ調査（2026-09-27）

- [FlightGearの整備済み空港一覧](https://wiki.flightgear.org/Developed_airports)にRJTTの掲載がある。
- [OurAirportsのRJTT滑走路情報](https://ourairports.com/airports/RJTT/runways.html)を位置・寸法の参照候補とする。
- [OurAirportsへの座標不一致の報告](https://ourairports.com/airports/RJTT/problem-reports/19399.html)がある。報告内容は未検証であり、数値を無条件に正解として採用しない。
- 風景データは未ダウンロード。滑走路の表示、標高、接地面、処理速度は未確認。
- 採用したシーンに対して滑走路の端点・進入端・幅・標高を照合し、描画と物理と評価の座標を統一する。
- 空港・機体モデル・エンジンのバージョンとライセンスは個別に記録する。

## 実装の順序案

1. 選定した機体とRJTTの表示・物理モデルの構成を検証し、滑走路を1方向選ぶ。
2. ゲームパッドで操縦・着陸できることを確認する。
3. 初期状態へのリセット、時刻を揃えた状態・入力の記録、再生を実装する。
4. 手動の着陸データから模倣学習を行う。学習・評価データは飛行単位で分ける。
5. 未使用の初期条件で成功率、接地位置、降下速度、姿勢、滑走路逸脱を評価する。

uvによるPython環境の構築とGPU・JSBSimの診断が完了。Windows版FlightGear本体を導入し、F310の認識・軸値読み取りを確認済み。FlightGear基本データも取得済み（2026-09-28にログと保存先を確認）。747-400・F-14Bの取得・飛行モデル読込と羽田周辺の地形取得を実施。C172Pも羽田34Rで初期化と短時間の物理計算を確認済み。[導入確認記録](simulator-validation.md) を参照。操縦・性能検証、データ収集、本課題の学習は未実施。詳細は [環境構築手順](environment-setup.md) を参照。

## シナリオを後から変更できる設計

ユーザーの要件として、シナリオは設定ファイルから変更できるようにする。
シナリオJSONの読み込みと起動時の適用を実装済み。進入状態・信号の実機確認は未実施。

- シナリオ設定：空港・滑走路と進入方向、開始位置・高度・速度・姿勢、風・時刻・視界、初期状態のばらつきと乱数seed、終了条件・成功条件。
- 機体設定：飛行モデルと外観モデルの識別子・版、操作入力との対応、重量・燃料・重心・トリム・脚・フラップ、許容範囲。
- 開始位置は滑走路に対する距離・横ずれ・相対高度で表現できるようにし、単位と高度基準を明示する。
- 空港・機体固有値を学習・記録コードに直書きしない。機種別の入力やシステムはアダプタで扱う。
- 実行時に解決した設定と機体・風景・コードの版を、各飛行ログと学習モデルに紐づけて保存する。
- 機体変更時は開始速度・トリム・操作範囲などの整合性を検証する。設定切替で同一の学習済みモデルが別機体を操縦できることは保証しない。

## コード先行の実装（2026-09-30）

ユーザーの指示により、実データ取得より先に収録→確認→学習→AI操縦→録画のコードを作成した。

- Windowsの標準ライブラリPythonでFlightGearの状態・操作を収録し、WSLのuv/PyTorchで学習する。AI推論はJSONに出力したMLPをWindowsで実行し、WindowsとWSLの間のUDP通信は不要とする。
- 数値状態17値から7操作を出す模倣学習を初期実装とする。画像入力は未実装。
- C172P、747-400、F-14BそれぞれにRJTT 34Rの仮の進入設定を追加。全エンジン同一推力、脚・フラップ固定。逆噴射等の機体固有操作は初期モデルの出力に含めない。
- 成功確認済みの手動飛行のみ学習対象にし、飛行単位で分割。別機体・別シナリオを混ぜない。現実装はシナリオ一致を要求し、未知条件の汎化試験は今後拡張する。
- 再現性のため設定と実装のハッシュを記録。重量・燃料・機体固有自動制御の完全な固定と記録、シーナリー版の固定は残作業。
- 模擬テストの合格と実際のAI着陸を区別する。実通信、ゲームパッド操作、機体の開始状態、録画はまだ実機確認前。

具体的な実行順は [着陸パイプライン](landing-pipeline.md) を参照。

## VLAへの拡張（2026-10-03）

ユーザーとVLAを使う方針に合意した。vLLM推論エンジンではなく、SmolVLAを対象にする。

- 画像・数値状態・自然言語指示から7操作を出力する。3機種は維持し、まずC172Pで一連の工程を確認する。
- 画像付き手動収録、追加学習前の操縦、手動データによる追加学習、学習後の操縦・録画・比較を実装する。
- SmolVLAは別のuv環境に依存関係を固定する。モデルとバックボーンのHubリビジョンも固定する。
- 推論中はシミュレーションを停止する初期方式とする。リアルタイム推論の性能測定・対応は後続課題。
- 学習前のモデルはロボットの事前学習重みを航空機の入出力へ対応させた基準。航空機の操縦を学習済みとは扱わない。
- 画像と状態の厳密な同期、重量・燃料・画角の固定、接地指標の実機照合、F310の操縦確認は残る。模擬入力のテストと実際の着陸性能を区別する。
- 固定指示だけでは言語理解の効果は測れない。画像・言語それぞれの効果を主張する場合は条件を揃えた追加比較が必要。

[実行手順と現実装の制約](vla-pipeline.md)を参照。


2026-10-03の到達点：実際のSmolVLA重みによるRTX 3060での模擬学習・保存・再読込、およびC172Pで画像→VLA推論→操作反映→MP4保存の短時間接続試験に成功。手動成功飛行データと実データによる追加学習、着陸性能の評価は未実施。起動時の時計停止と機体初期化によるフラップ上書きは、実行直前の設定適用で対応した。
