# 最終課題：人の操縦から学ぶAIの着陸

## 合意した方向性

- タスク：滑走路が視界に入っている最終進入から着陸する。
- 空港：羽田空港（HND / RJTT）。初期プリセットは34Rへの進入。
- 機体：実在機を模擬したモデルを使用する。2026-09-27に、旅客機はBoeing 747-400（GE CF6-80C2B1F）、戦闘機はF-14Bに確定した。2026-09-28にCessna 172P（FlightGear基本データ同梱版）を追加し、3機種で着陸課題に取り組む。3機種の操縦・性能は未検証。詳細は [機体選定](aircraft-selection.md) を参照。
- データ収集：受講者がゲームパッドで操縦し、機体状態と操縦入力を記録する。
- AI：操縦データからの模倣学習を軸にする。2026-10-03にSmolVLAの追加学習と学習前後の比較を採用。数値入力MLPも比較対象として保持。
- 利用可能な環境：WSL2上のUbuntu 22.04.5、RTX 3060（12GB）、WindowsにUSB接続したLogicool F310。CPU・RAMは未確認。
- Python環境管理：uv。

1. 選定した機体とRJTTの表示・物理モデルの構成を検証し、滑走路を1方向選ぶ。
2. ゲームパッドで操縦・着陸できることを確認する。

## シナリオを後から変更できる設計

ユーザーの要件として、シナリオは設定ファイルから変更できるようにする。
シナリオJSONの読み込みと起動時の適用を実装済み。進入状態・信号の実機確認は未実施。

- シナリオ設定：空港・滑走路と進入方向、開始位置・高度・速度・姿勢、風・時刻・視界、初期状態のばらつきと乱数seed、終了条件・成功条件。
- 機体設定：飛行モデルと外観モデルの識別子・版、操作入力との対応、重量・燃料・重心・トリム・脚・フラップ、許容範囲。
- 開始位置は滑走路に対する距離・横ずれ・相対高度で表現できるようにし、単位と高度基準を明示する。
- 空港・機体固有値を学習・記録コードに直書きしない。機種別の入力やシステムはアダプタで扱う。
- 実行時に解決した設定と機体・風景・コードの版を、各飛行ログと学習モデルに紐づけて保存する。
- 機体変更時は開始速度・トリム・操作範囲などの整合性を検証する。設定切替で同一の学習済みモデルが別機体を操縦できることは保証しない。

## VLAへの拡張（2026-10-03）

ユーザーとVLAを使う方針に合意した。vLLM推論エンジンではなく、SmolVLAを対象にする。

- 画像・数値状態・自然言語指示から7操作を出力する。3機種は維持し、まずC172Pで一連の工程を確認する。
- 画像付き手動収録、追加学習前の操縦、手動データによる追加学習、学習後の操縦・録画・比較を実装する。
- SmolVLAは別のuv環境に依存関係を固定する。モデルとバックボーンのHubリビジョンも固定する。
- 推論中はシミュレーションを停止する初期方式とする。リアルタイム推論の性能測定・対応は後続課題。
- 学習前のモデルはロボットの事前学習重みを航空機の入出力へ対応させた基準。航空機の操縦を学習済みとは扱わない。
- 画像と状態の厳密な同期、重量・燃料・画角の固定、接地指標の実機照合、F310の操縦確認は残る。模擬入力のテストと実際の着陸性能を区別する。
- 固定指示だけでは言語理解の効果は測れない。画像・言語それぞれの効果を主張する場合は条件を揃えた追加比較が必要。

[実行手順と現実装の制約](vla-pipeline.md)を参照。

2026-10-11：課題要件を10/8版に更新（動画1〜3分、YouTube提出、GitHubはpublic必須、提出開始10/19）。フラップは操縦・学習の対象外とし、シナリオで事前に設定する方針に決定。

flight-001のフラップ変化の原因を特定した。FlightGear同梱C172Pの `Nasal/state-manager.nas` は空中開始時にタイマーを登録し、シミュレーション時間で5秒後に `/sim/presets/offset-distance-nm` に応じてフラップとスロットルを設定する。座標指定で開始するため距離は0となり、フラップ1.0・スロットル0.75が設定される。記録では物理計算の再開から約5.0秒後にフラップ0.3333→1.0とスロットル0.35→0.75が同じサンプルで変化しており、この処理と一致する。F310の既定割当（`Input/Joysticks/Default/joystick.xml`）にはフラップの割当がない。

対策として、収録開始前に物理計算を停止したまま時計だけを進めてタイマーを消化し（C172Pシナリオの `startup_settle_seconds: 6`）、その後に設定を再適用する処理を追加した。収録中にフラップが変わった場合は戻し、そのサンプルは記録しない。模擬テストで確認済み。

同日のFlightGear実機確認で、この待機方式は使えないとわかった。物理計算の停止（`/sim/freeze/master`）を指定したまま時計を6秒進めると、機体は約226 m前進し26 ft降下した（75 ktで6秒の飛行に相当）。タイマーも発火し、フラップ1.0・スロットル0.75になった。起動直後は物理計算の停止が解除され、時計だけが停止した状態だったが、機体は止まっていた。このFlightGearでは時計の停止が実質的な一時停止になっている。待機方式を削除し、収録中にフラップの変化を検知したら、フラップをシナリオの値に、スロットルを直前の値に戻してそのサンプルを記録しない方式に変更した。収録開始の条件は、物理計算と時計のどちらかが停止していることに緩めた。

変更後の診断収録（`datasets/c172p/check-20261011-seed0`、番号0、20秒）で、5.04秒の上書きを1回検知・復元した。記録370サンプルでフラップ0.3333・トリム0・ブレーキ0・脚は一定。ただし、フラップを先に戻したため、スロットル0.75のサンプルが1つ記録されていた。スロットルを先に戻す順序に修正した。また、シミュレーション時刻2.0→3.0秒でパケットが1秒途切れた（取りこぼしなし。FlightGearのフレーム停止と推定、原因未確認）。スロットル0.35のまま水平付近を保つと、速度は20秒で75→56 ktに低下した。進入用のスロットル・トリムは着陸試験で調整する。VLAの指示文から減速の指示（slow down）を削除した。

最初の着陸試験（`datasets/c172p/check-20261011-landing1`、番号1）では、自動終了・上書きの復元・固定設定が機能した。接地は進入端から1180 m、中心線から4 m、降下率8.5 ft/s、ピッチ-0.5度、機首方位のずれ-6.4度で、主脚からの接地と機首方位が不合格だった。進入端を約285 ft（3度の経路では約50 ft）で通過して急降下しており、画面だけでは経路の高低を判断しにくいことが主因と考えた。接地後に機首下げ約6度で滑走しており、前脚の折損が疑われる。地表の標高の推移から、滑走路の座標が描画と一致することも確認した。速度計の針は、3時の方向が約62〜65 kt。

対応として、収録中の進入ガイド表示、終了時の損傷判定（`no_damage`）、短い結果表示を追加した。開始時の速度を70 kt、スロットルを0.5に変更した。

2026-10-12：手動収録7回のうち6回（`flight-002`〜`007`）を保存した。当初の判定では全て不合格で、6回中5回がバウンドだった。接地後に浮いた高さを調べると0.3〜3.8 ftで、うち3回は0.5 ft以下の軽い跳ねだった。左主脚の接地信号だけで判定していたため、厳しすぎたと判断した。バウンドは「接地時から2 ft以上浮く」に変更した。中心線の不合格が残り、進入中に中心線の左右へ20〜30 m幅で蛇行していた。中心線の基準は、ユーザーの判断で10 mから15 m（滑走路幅60 mの4分の1）に緩めた。エルロンの効きは既定のまま。評価の基準・進入ガイド・損傷判定の設定はタスク条件ではないため、シナリオのハッシュから除外した（旧方式のハッシュも受け付ける）。一覧・ラベル付け・比較は最新の基準で評価する。この結果、`flight-006`と`007`が全項目に合格した。トリムは使わず0に固定する方針を維持する（ユーザー判断）。

2026-10-12：人の手動収録は10回中3回分（`flight-008`〜`010`）が保存され、いずれも不合格だった（バウンド・中心線）。成功は計2回にとどまり、ユーザーと相談して、**人の操縦と自作の自動着陸の両方を学習に使う**方針に決めた。C172Pには組み込みの自動着陸がない（KAP140は進入まで）ため、PID制御の自動着陸 `landing/autoland.py` を作成した。記録上の操縦者は `expert` とし、人の飛行と同じ審査（全項目の合格・動画確認・ラベル）を経て学習に使う。

FlightGearのC172P飛行モデルをWSL上のJSBSimで動かす事前確認環境（`scripts/offline_autoland.py`）を作った。FlightGear専用のプロパティは要求されたものだけを作成し、係留の計算は力0に置き換え、燃料（各翼20 gal）とパイロット（170 lb）は近似した。手を離した飛行で、FlightGearと同様に機首が上がって減速することを確認した（8秒後：FlightGear 62.6 kt・3.8度、オフライン65.1 kt・5.1度）。オフラインでは、番号0〜30と評価用の1000・1001で全て合格した。接地は進入端から約364 m、降下率約1.2 ft/s、ピッチ約3.8度、バウンド0.2 ft。2 NMの間に同じ経路へ収束するため、接地付近の状態はほぼ同じになる。FlightGear上での確認はこれから。

人の飛行 `flight-002`〜`010` は画像なし（`--images` なし）で収録していた。案内した手順の誤りで、VLAの学習には使えない（MLPには使える）。`scripts/fly_c172p.ps1` を画像付き（0.2秒間隔）に修正し、自動着陸の `-Autoland` を追加した。

FlightGearでの最初の自動着陸（`expert-101`）は、開始約20秒で背面飛行になり墜落した。画像の取得（1枚0.3〜0.9秒）の間は制御が止まる実装のため、制御が毎秒約1.7回に落ちて発振した（オフライン検証は画像を取得しないため再現しなかった）。自動着陸では、画像取得の間シミュレーションを一時停止する方式（`execution_mode: paused_capture`）に変更した。シミュレーション時間では毎秒20回の制御を保ち、画像と状態が同時刻になる。実時間と録画は一時停止を含む。人の手動収録では一時停止しないため、画像取得の遅れがVLA学習の対応付けの条件（取得0.25秒以内）を満たすかは、画像付きの収録で確認が必要。
