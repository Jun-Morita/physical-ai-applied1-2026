## 1. 概要

フライトシミュレーターFlightGearで、セスナ172P（C172P）を羽田空港の滑走路34Rに着陸させるタスクを、AIに学ばせた。

- AIには、操縦席から見た**画像**、「羽田の34Rに着陸し、滑走路上にとどまれ」という**指示文**、**機体の状態**（位置・速度・姿勢など）を入力する。
- AIは、**操縦桿（エルロン・エレベーター）・ラダー・スロットル**の4つの操作を出力する。
- モデルには、ロボットアーム向けに公開されている視覚・言語・行動モデル（VLA）の**SmolVLA**を使った。自作の自動着陸プログラムの飛行48回で追加学習し、学習前後の操縦を同じ開始条件で比べた。

**結果**（評価5ケース。ケースごとに飛行の開始位置が異なる）：学習前は5回とも開始15〜19秒で機体が裏返り、海に落ちた。追加学習後は5回とも接地帯（進入端から195〜574 m）に接地し、脚の損傷もなかった。うち1回は、接地目標（400 m）のほぼ真上の396 mに接地し、全11項目に合格した。残りの4回は、バウンドや接地時の機首方位のずれで不合格だった。

## 2. 目的

- **ロボット以外の「身体」へのPhysical AIの応用**：講座で扱ったロボットアームや移動ロボットの考え方（画像と言語から行動を出すVLA）が、航空機という異なる身体の、連続的で失敗の許されない制御に通用するかを確かめる。
- **事前学習モデルの追加学習の効果を測る**：同じ開始条件で学習前後を比べ、何ができるようになり、何が足りないかを数値で示す。
- **実用への接点**：着陸は飛行で最も事故の多い段階である。画像から状況を判断する操縦支援や、パイロット訓練の評価の自動化につながる題材として選んだ。

## 3. タスクの設計

| 項目 | 内容 |
| --- | --- |
| 環境 | FlightGear 2024.1（Windows）、羽田空港RJTT、滑走路34R、昼・無風 |
| 機体 | セスナ172P（単発のプロペラ機） |
| 開始 | 滑走路の2 NM（約3.7 km）手前、3度の進入経路上、時速約70 kt。乱数で横±100 m・高さ±60 ft・方位±5度・速度±5 ktずらす |
| 操作 | エルロン・エレベーター・ラダー・スロットルの4つ。フラップ・トリム・ブレーキは固定 |
| 終了 | 接地の5秒後（減速・停止は対象外）。墜落・着水したら自動で終了 |
| 評価 | 墜落なし、接地位置（進入端から0〜900 m）、中心線からのずれ（15 m以内）、接地直前の降下率、バンク角、主脚からの接地、機首方位、バウンドなし、滑走路内の滑走、脚の損傷なし など11項目。すべて合格で成功 |

- 成功の条件は、要件定義として、実装を始める前に数値で決めた。
- 開始位置の乱数の番号は、学習用（1〜999）と評価用（1000以上）を分けた。評価は学習に使っていない開始位置で行う。
- 接地の目標は、ICAOが定めるエイミングポイント（進入端から400 m）とした。
- 動画を1〜3分にまとめられるよう、タスクを「最終進入から接地まで」に絞った。

## 4. システム構成

<図2：構成図。Windows上のFlightGear ⇔ 収録・操縦プログラム ⇔ WSL上のSmolVLA推論ワーカー>

- **FlightGear（Windows）**：機体の状態を毎秒20回UDPで送り、操作をUDPで受け取る。設定の読み書きや一時停止はHTTPで行う。連続して流れる状態と、必要なときだけ行う要求とを分けたのは、ROS 2のトピックとサービスの役割分担にならったものである。画面は画像として取得する。
- **収録・操縦プログラム（Python）**：状態・画像・操作を記録し、着陸を11項目で自動評価する。開始位置の確認、機体側スクリプトによる操作の上書きの検知と復元、墜落時の自動終了も行う。
- **SmolVLA推論ワーカー（WSL、RTX 3060）**：画像・指示文・状態を受け取り、4つの操作を返す。推論の間はシミュレーションを一時停止し、0.2秒（シミュレーション時間）ごとに操作を更新する。そのため今回の飛行はリアルタイムではなく、実時間はシミュレーション時間の約3.5倍かかる（リアルタイム化は今後の課題）。
- 環境構築はuvで固定し、READMEに再現手順を記載した。

## 5. 学習データ：自作の自動着陸を「お手本」にする

- まずゲームパッドで手動着陸を収録したが、17回中2回しか全項目に合格せず、学習に足りなかった。
- そこで、機体の状態を読んで4つの操作を出す**PID制御の自動着陸プログラム**を作った。中心線と進入経路を追い、速度をスロットルで保ち、高さ20 ftから機首を上げて降下を弱める（フレア）。従来の制御でお手本を作り、それをAIが学ぶという、AIと制御の組み合わせ方である。
- 自動着陸の飛行も、人の飛行と同じく、**全項目の合格と動画の目視確認**を経たものだけを学習に使った。
- お手本が常に理想の経路を飛ぶと、AIは「ずれから戻る」操作を学べない。そこで、開始時のずれを広げた条件（高さ±150 ft・横±150 m、開始距離1・1/2・1/4）の飛行を加えた。
- 最終的な学習データは48回分で、画像は学習用9917枚・検証用2995枚。

## 6. AIモデル：SmolVLAの追加学習

| 項目 | 内容 |
| --- | --- |
| モデル | SmolVLA（LeRobot 0.4.3、`lerobot/smolvla_base`）。視覚・言語モデルSmolVLM2をもとに、ロボットの操作を出力するよう学習済み |
| 入力 | 画像（256×256）、英語の指示文、機体の状態17個（滑走路からの距離・横ずれ・高さ、速度、姿勢、角速度、接地の有無） |
| 出力 | 4つの操作（−1〜1に正規化） |
| 学習 | 画像1枚ごとに、その瞬間の状態とお手本の操作を1組にして学習。バッチ8、15000ステップ（学習用画像を約12周）、RTX 3060で約1時間 |

- SmolVLAは、重み・学習コード・学習データまで公開されたVLAで、追加学習と再現がしやすい点で選んだ。
- ロボットアーム用の入出力を、航空機の状態・操作の数に合わせて付け替えた。事前学習は飛行を含まないため、学習前に着陸できることは想定していない。
- 機体の状態は、学習データの平均と標準偏差で正規化して入力する（7.2節）。

## 7. 結果

### 7.1 学習前後の比較（FlightGear、評価用の番号1000〜1004）

| 項目 | 学習前（5回） | 学習後（5回） |
| --- | --- | --- |
| 接地まで飛べた | 0 | 5 |
| 墜落なし・脚の損傷なし | 0 | 5 |
| 降下率・バンク・主脚からの接地 | 0 | 5 |
| 接地位置（0〜900 m） | 0 | 5 |
| 中心線（15 m以内） | 0 | 4 |
| 滑走路内の滑走 | 0 | 4 |
| 機首方位（5度以内） | 0 | 3 |
| バウンドなし（2 ft以内） | 0 | 2 |
| **全項目に合格** | **0** | **1** |

| 番号 | 接地位置 | 中心線 | 降下率 | 機首方位 | バウンド | 判定 |
| --- | --- | --- | --- | --- | --- | --- |
| 1000 | 396 m | 8.7 m | 2.0 ft/s | 4.7° | 0.1 ft | 合格 |
| 1001 | 412 m | 25.7 m | 3.9 ft/s | 4.5° | 3.2 ft | 中心線・バウンド・滑走 |
| 1002 | 195 m | 0.5 m | 2.9 ft/s | 1.1° | 3.6 ft | バウンド |
| 1003 | 273 m | 5.6 m | 7.9 ft/s | 5.3° | 2.2 ft | 機首方位・バウンド |
| 1004 | 574 m | 8.7 m | 0.1 ft/s | 12.0° | 0.0 ft | 機首方位 |

- 学習前は、開始直後から極端な操作をして機体が裏返り（傾き約180°）、5回とも開始15〜19秒で海に落ちた。
- 学習後は、翼をほぼ水平に保って進入経路に沿って降下し、5回とも接地帯に接地した。番号1000は接地目標の400 m点のほぼ真上（396 m）に接地し、動画でも着陸を確認した。
- 残った課題は、接地時のバウンド（2.2〜3.6 ft）と、機首方位のずれ（最大12度）である。

### 7.2 開発の経過

| モデル | 番号1000の結果 |
| --- | --- |
| 学習前 | 13秒で海に落ちた |
| 追加学習3000ステップ | 降下せず高度約800 ftを保ち、滑走路を越えて3310 mに接地 |
| 追加学習15000ステップ | 前半は上昇し、進入端を過ぎてから降下。2732 m・滑走路の横に接地 |
| 状態を正規化して6000ステップ | 経路に沿って降下し、181 mの滑走路上に接地（左右のずれで不合格）。5回中、接地帯に入ったのは1回で、多くは経路より50〜80 ft低めを飛び、進入端の手前に接地した |
| **状態を正規化して15000ステップ** | **396 mに接地し、全項目に合格。5回とも接地帯に接地** |

最初の2つが降下しなかった原因は、状態の入力の前処理にあった。状態を固定の値で割って入力していた（高さ÷1000 mなど）ため、経路から150 ftずれても入力値は0.046しか変わらず、高さのずれがモデルにほとんど見えていなかった。学習データの平均と標準偏差で正規化すると、初めて経路に沿って降下した。

## 8. 工夫した点

1. **評価を厳密にした**：接地位置・中心線・降下率・バウンド・脚の損傷など11項目を自動で判定する。全項目合格に加え、動画の目視確認を経た飛行だけを学習に使った。
2. **丸覚えを防ぐ評価設計**：開始位置を乱数でずらし、学習用と評価用の番号を分けた。学習前後を同じ番号の組で比べた。
3. **お手本を自作して、データの質と量を確保した**：手動操縦では成功が少なかったため、自動着陸プログラムを作り、ずれを広げた開始条件で「戻し方」の手本も集めた。
4. **画像・状態・操作の時刻をそろえた**：取得時刻・受信時刻・シミュレーション時刻を区別して処理時間を測ると、画像の取得に0.3〜0.9秒かかり、20 Hzの制御に間に合わなかった。そこで取得中はシミュレーションを止める。止めた瞬間の画像・状態と、その状態に対するお手本の操作を1組にした。
5. **シミュレーター特有の問題への対処**：C172Pは空中開始の5秒後に機体側のスクリプトがフラップとスロットルを上書きする。これを検知して戻し、その時点の記録は学習から除いた。
6. **再現性**：MLOpsで学んだ版の管理を実践した。環境をuvで固定した。開始条件・評価基準・モデルの由来（ハッシュ）を記録に残し、収録から比較までをコマンドで再現できるようにした。

## 9. 試行錯誤と考察

- **お手本の「ずれから戻る」場面がないと、模倣したAIは崩れる**：自動着陸25回で学習した小さなニューラルネット（MLP）は、検証誤差が0.0001程度と小さかった。それでも飛ばすと、経路から少しずれたまま戻せずに滑走路の手前に降りた。データの量より、状態の幅が重要だった。
- **検証誤差の小ささは着陸の成否を保証しない**：MLPは、同じデータでも学習の乱数次第で合格数が0〜3/10と変わった。検証誤差が最も小さいモデルも着陸できなかった。評価は必ずシミュレーターで飛ばして行った。
- **前処理が性能を大きく左右した**：SmolVLAが降下しない原因を、同じ場面でのお手本の操作と並べて比べて切り分けたところ、入力の前処理の不備に行き着いた。大規模な事前学習モデルでも、数値の入力のスケールが不適切だと、重要な情報（高さのずれ）を使えなかった。
- **開発用のシミュレーターと本番の違いに注意**：高速に試すため、FlightGearを使わずにJSBSim（同じ飛行モデル）を直接動かす環境を作った。しかし、ラダーの符号と前輪の操向がFlightGearと異なり、接地後の失敗を誤ってAIのせいだと判断しかけた。本番の記録と同じ操作をして挙動を比べ、気づいた。シミュレーターと実機のずれ（sim2real）と同じく、検証に使う環境が本番と同じ挙動をするかを先に確かめる必要がある。
- **地図データの食い違い**：滑走路の座標を現実の最新データから取ったところ、シミュレーターに描画される滑走路と355 mずれていた。動画を見て「滑走路の端ぎりぎりを狙っている」と気づき、描画と同じデータに直した。
- **判定基準の見直し**：引き起こし後にわずかに浮いてから接地する柔らかい着陸を、「上昇中の接地」として不合格にしていた。数値と動画を見て、基準を見直した。

## 10. 今後の課題と応用

### 10.1 今後の課題
- **学習データが不足する場面への対応**：お手本の飛行は、ほとんどが正常な進入経路に沿っている。そのため、次のような場面の手本が少なく、AIはそこから立て直す操作を十分に学べていない。
    - 進入経路から大きく外れた異常な経路を、正常な経路に戻す場面
    - 速度が落ちて失速に近づく場面（自動着陸の収録でも、27回中3回が進入中に失速して着水した）
    - 引き起こしから接地直後にかけて、横に流れたり機首がずれたりする場面

    これらの場面を意図的に作ってお手本を集める、AIが実際に陥った状態でお手本の操作を教える（DAgger）などの方法で、データを補う必要がある。

- 接地時のバウンドと機首方位のずれを減らし、全項目の合格率を上げる（フレアから接地直後の手本の追加、操作を数ステップ先まで予測する設定など）。
- リアルタイム化：今回は画像の取得と推論の間シミュレーションを止めている。低精度化（bf16）では推論は速くならず、ノイズ除去の反復回数を10回から5回に減らすと時間がほぼ半分になった（実測）。操作をまとめて予測する、画像の取得や通信を軽くする、などを組み合わせ、推論中の状態の遅れも含めて評価し直す。
- 評価の回数を増やし、成功率を統計的に示す。
- 横風や視界の悪化など、条件を変えた汎化を調べる。

### 10.2 今後の応用：旅客機・戦闘機への展開
小型機のほかに、性質の大きく異なる2機種も、同じ羽田34Rへの進入として準備した。

| 機種 | 特徴 | 準備した内容 |
| --- | --- | --- |
| Boeing 747-400（旅客機） | 大型で慣性が大きく、操作への反応が遅い | 機体データの版を固定して導入。羽田34Rへの進入シナリオ（開始高度・評価基準）を作成 |
| F-14B（戦闘機） | 高速で、操作への反応が速い | 同上。FlightGear 2024.1で動かすための修正パッチを作成 |

収録・評価・学習のプログラムは機種に依存しない作りにしており、機種ごとにお手本を集めて追加学習できる。同じVLAが、反応の速さの異なる「身体」にどこまで適応できるかを比べることが、次の段階の目標である。

## 付録：再現方法

READMEに、環境構築（uv）、FlightGearの起動、収録、学習、評価、比較のコマンドを記載している。

- 自動着陸の収録：`scripts/fly_c172p.ps1 -Seed <番号> -Autoland [-StartProfile wide|wide-half|wide-quarter]`
- SmolVLAの追加学習：`python -m landing.vla train <飛行> --base runs/vla/c172p-base-aim400 --output <出力> --steps 15000 --batch-size 8`
- 評価：`scripts/fly_c172p.ps1 -Seed 1000 -VlaBridge <ワーカーのディレクトリ>`
- 比較：`python -m landing.compare --before <学習前> --after <学習後> --output <出力>`
